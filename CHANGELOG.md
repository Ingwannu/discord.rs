# Changelog
All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased

### Fixed
- **The HTTP interactions endpoint can apply a default `allowed_mentions`.** The endpoint encoded inline responses with no default, while `RestClient::create_interaction_response` fills in the client's (`RestClientBuilder::default_allowed_mentions`), so the same reply pinged differently depending on the transport, and the endpoint, which takes no `RestClient`, had no way to be configured. `InteractionsEndpointBuilder::default_allowed_mentions` now sets it for raw and typed handlers and `AppFramework` routes, with the REST rule: only message callbacks (types 4 and 7) get it, a value set on the response wins, and `InteractionResponse::Raw` is sent as written. One response and one policy encode to the same bytes on both transports. Without the setting the endpoint answers as 3.0.0 did.
- **Docs no longer show a racy "respond later" pattern.** The `AppFramework` and interactions-endpoint pages (English and Korean) spawned a task that calls `edit_reply` while the route returned an inline `defer`; the task can run before the endpoint records the deferral (and before Discord receives it) and then fails with "interaction has not been acknowledged". The examples now defer over REST, spawn the task, and return `EndpointReply::Accepted`, and the `AppContext` and `TypedInteractionHandler` docs say so.
- **Docs describe the 3.0 API.** Text left over from 2.x is corrected in the README, `USAGE.md`, and the docs site (English and Korean): gateway dispatch described as an "`Event` enum" (3.0 shares one `Event` envelope as `Arc<Event>` and matches on `EventKind`); `edit_message`, `create_dm_channel`, `create_interaction_response`, and `bulk_overwrite_global_commands` called "no longer public" (they are the 3.0 typed methods); "raw `serde_json::Value` methods" and a generic `edit_current_application` as the escape hatch (now `RestClient::request(RawRequest)`); `message.id.as_str()`, `&ctx.id`, and the removed `Error` alias in examples and signatures; deprecated helpers (`followup_message`, `defer_interaction`, `update_interaction_message`) recommended over `InteractionResponder`; the wrong error text for an early follow-up; `GatewayClient` listed as public; a `RawInteraction` match without the `Autocomplete` arm; the Korean docs' "2.2.0" version line and `BotClient`/`DiscordHttpClient` diagram; and the full manual's 2.x gateway hooks and export list, endpoint response variants, and crate-private parser helpers. `RestClientBuilder::default_allowed_mentions` named the 2.x `update_message` instead of `edit_message`.
- **Voice works in DAVE (end-to-end encrypted) channels.** Discord requires DAVE in every voice channel except Stage channels since 2026-03-01 and closes connections without it with code 4017. 3.0.0 advertised DAVE support in IDENTIFY but never ran the MLS session, so in those channels an `AudioPlayer` subscribed with `subscribe_runtime` played nothing while logging a warning per frame, and `send_opus_frame`/`recv_voice_packet` returned errors. A runtime connected with the new `connect_voice_runtime_with_options(config, VoiceConnectOptions::new(channel_id))`, which the new `Context::connect_voice_runtime_with_dave` uses, runs DAVE itself, as @discordjs/voice and Songbird do: it sends its MLS key package after SESSION_DESCRIPTION, applies the voice gateway's external sender, commits proposals for members who join (refusing users absent from CLIENTS_CONNECT), processes commits and welcomes, answers `prepare_transition`/`execute_transition`/`prepare_epoch` (switching its sending key only when a transition executes, as the protocol requires, so members that have not processed a commit yet can still decrypt it), follows downgrades to transport-only encryption and upgrades through a new group, and reports an invalid commit or welcome (`dave_mls_invalid_commit_welcome`) and rejoins with a new key package (also after more than 36 undecryptable frames outside any transition). `send_opus_frame`, `send_opus_frame_after_gap`, `play_opus_frames`, and `AudioPlayer` encrypt each Opus frame with DAVE before transport encryption (the Opus silence frame stays unencrypted, as the protocol allows); `recv_voice_packet` and `recv_decoded_voice_packet` decrypt each speaker with that user's key and skip packets that cannot be decrypted around MLS transitions instead of returning errors. Messages that arrive during the voice handshake (CLIENTS_CONNECT, the external sender) were dropped; they are now handled once the session starts. Hermetic tests run two independent `davey` sessions and a test-only voice gateway through the whole flow, including real Opus audio from `AudioPlayer`; the path has not been run against live Discord yet (`tests/live_voice_dave.rs`, ignored).
- **No silent playback into a call that cannot hear it.** On such a runtime, until it has a media key in use, sends return a `DiscordError::Voice` that says why and transmit nothing (no sequence number, timestamp, or nonce is used up) instead of sending audio unencrypted into an end-to-end encrypted call, and `AudioPlayer` treats the connection as not playable: with the default `NoSubscriberBehavior::Pause` it waits in `AutoPaused` and then plays the track from its first frame. Alone in a DAVE channel, the group forms when someone joins. A connection whose sends fail is reported once per stretch of failures (`AudioPlayer::connection_events`, and one warning) instead of one warning per frame.
- **Other members' voice states no longer overwrite the bot's voice connection.** The gateway context applied every VOICE_STATE_UPDATE of a guild to its tracked voice connection, so another member joining or moving replaced the bot's channel and session ID, and another member leaving cleared the connection; `Context::connect_voice_runtime` then authenticated with the wrong session or reported missing configuration. The context now records the bot's user from READY and applies only the bot's own voice states (`VoiceManager::update_own_voice_state`); the cache and event handlers still see every member's.
- **A 4017 close explains itself.** Closes during the voice handshake now return an error with the close code and Discord's meaning instead of "voice websocket closed unexpectedly"; for 4017 the error says that Discord requires DAVE in the channel, what the connection advertised, and, for `connect_voice_runtime`, to use `connect_voice_runtime_with_options`.

### Security
- **Keep the `davey` crate's trace logging off.** davey, the DAVE library behind the voice runtime, writes media key secrets (every member's MLS-exported sender secret, ratchet keys) to `tracing` at trace level, so a `RUST_LOG=trace` or `davey=trace` log holds keys that decrypt captured call audio. This has been so since 3.0.0's `dave` feature (`VoiceDaveySession`); davey 0.1.5, the latest release, still does it, and a dependency cannot be patched from here. Keep the `davey` target at `info` or coarser (for example `RUST_LOG=info,davey=info`). The runtime and `VoiceDaveySession::new` now log a warning when a DAVE session starts while davey's trace level is enabled. An upstream issue is drafted in `docs/design/dave-voice.md`.
- The runtime's own DAVE key material (exported sender secrets, pending per-transition secrets, ratchet secrets, derived keys, HKDF intermediates) is cleared when replaced or dropped (`zeroize`, already part of the `voice` build) and is not reachable through `Debug`. The AES key schedule inside the frame cipher and HMAC's internal state are not cleared by those crates on every target.

### Added
- `InteractionsEndpointBuilder::default_allowed_mentions(AllowedMentions)` (see Fixed).
- `connect_voice_runtime_with_options(config, VoiceConnectOptions)` (`voice_runtime::connect_with_options`) and `VoiceConnectOptions` (`#[non_exhaustive]`, `VoiceConnectOptions::new(channel_id)`): connect a voice runtime that runs DAVE itself. DAVE uses the voice channel as its MLS group, which the voice gateway does not report. `VoiceManager::runtime_options(guild_id)` builds the options from the tracked voice state.
- `VoiceManager::{set_current_user, current_user, update_own_voice_state}`: track only the bot's own voice state (see Fixed). `update_voice_state` keeps applying any member's.
- `Context::connect_voice_runtime_with_dave(guild_id, user_id)`: the same from the voice state a gateway `Context` tracks (session, token, endpoint, channel). `Context::connect_voice_runtime` stays as in 3.0.0.
- `VoiceRuntimeHandle::{dave_status, subscribe_dave_status, is_playable, wait_until_playable, dave_verification_code}` and `VoiceDaveStatus` (protocol version, readiness, epoch, voice privacy code, last transition, last error, undecryptable packets, recoveries, `can_send_audio()`).
- `VoiceFrameSink::is_playable` (default `true`): the player counts only playable sinks as subscribed, as `@discordjs/voice` does with `AudioPlayer.playable`.
- `AudioPlayer::connection_events()` with `PlayerConnectionEvent::{SendFailed, Recovered}`, and `PlayerSubscription::id()`.

### Changed
- The `voice` feature includes DAVE (`davey`): voice without it can only join Stage channels. A clean build of `voice` takes about 6 s longer (41 s → 47 s on the reference machine) and pulls about 100 more crates, all pure Rust. The `dave` feature remains as an alias of `voice`, and the APIs that were behind it (`VoiceDaveySession`, `VoiceDaveFrameEncryptor`, `send_opus_frame_with_dave*`, the `send_dave_*` commands) are available with `voice`.
- `connect_voice_runtime(config)` and `Context::connect_voice_runtime` are unchanged: they advertise DAVE as configured and leave the session to the caller, as in 3.0.0; their handles report `is_playable() == true`, so `AudioPlayer` behaves as before with them.
- On a `connect_voice_runtime_with_options` runtime, IDENTIFY's `max_dave_protocol_version` is capped at the version this crate implements (1), and `recv_voice_packet_with_dave` decides whether a frame is DAVE-encrypted from the runtime's current DAVE version (which follows transitions).
- `davey` 0.1.5 is required (0.1.3 took the later of two passthrough deadlines where libdave takes the earlier, and did not check frame-encryption buffer sizes).
- Known limits, documented in the voice guide: the voice runtime has no RESUME loop (a reconnect is a fresh IDENTIFY and a fresh MLS join), and davey 0.1.x does not yet check a welcome's members against the call (an upstream TODO; commits and proposals are checked).
- Messages that arrive during the voice handshake are kept for the runtime instead of dropped, on both entry points, so the raw `VoiceRuntimeState::dave` mirror also sees an external sender that came before SESSION_DESCRIPTION.

### Migration notes
- Nothing breaks: `VoiceRuntimeConfig` is unchanged, and `connect_voice_runtime(config)` keeps 3.0.0's DAVE behaviour, including hand-driven MLS with `VoiceDaveySession` and the raw `send_dave_*` commands. All additions are new items, a defaulted trait method (`VoiceFrameSink::is_playable`), and `#[non_exhaustive]` types, so this is a minor release (3.1.0).
- To hear audio in DAVE channels, connect with `connect_voice_runtime_with_options(config, VoiceConnectOptions::new(channel_id))`, or use `Context::connect_voice_runtime_with_dave`. Do not drive MLS by hand on such a runtime: it sends its own key package, and the voice gateway would see two. Custom frame encryption through `send_opus_frame_with_dave` / `recv_voice_packet_with_dave` still works.
- Handles from the new entry points refuse to send audio, and an `AudioPlayer` treats them as not playable, until the runtime has a media key in use. With `NoSubscriberBehavior::Stop`, call `VoiceRuntimeHandle::wait_until_playable()` before `play`.

## 3.0.0 - 2026-10-18

2.1.0 and 2.2.0 were never published to crates.io and already change public types relative to 2.0.2, so the next release is 3.0.0. The phased plan is in `ROADMAP.md`.

### Fixed
- **REST retries no longer duplicate mutations.** 5xx responses, timeouts, and failed response reads are retried only for requests that are safe to repeat: GET, HEAD, OPTIONS, PUT, and DELETE, plus `POST /channels/{id}/messages` with `nonce` + `enforce_nonce: true` (the only route Discord deduplicates), and that one only within 60 seconds of the first attempt, because Discord's nonce check covers just "the past few minutes". Previously a POST whose response was lost was sent again, which could post the same message twice. 429s are always retried; connection failures are retried for every method only on clients built by this crate (see below).
- **No redirects on the managed transport.** Clients from `RestClient::new` and `RestClientBuilder::build` no longer follow redirects, so a connect failure proves the request was never delivered. With `RestClientBuilder::use_client(...)` the redirect policy is unknown, so POST/PATCH are not retried after connect failures.
- **Rate-limit buckets respect major parameters.** A learned `x-ratelimit-bucket` hash is combined with the route's channel/guild/webhook/interaction-token scope before it blocks requests, so a 429 in one channel no longer stalls requests to other channels that report the same hash. Requests are serialized per resolved bucket, and a request that queued before its bucket was known moves to the bucket's gate instead of running beside it. A shorter concurrent observation no longer cuts an outstanding block short.
- **Tokens stay out of REST diagnostics.** Rate-limit route keys digest webhook and interaction tokens; transport errors and API/proxy error text are scrubbed of the exact request token; `HttpError` additionally redacts tokenized URL paths. `RateLimitInfo::route`, `DiscordError::RateLimit`, `DiscordError::Api`, `DiscordError::Http`, and REST log lines no longer contain tokens. (`Debug` output of interaction contexts and OAuth2 error bodies are scheduled for phase 3; see `ROADMAP.md`.)
- **Malformed wait headers cannot panic.** `inf`, `NaN`, negative, or huge `Retry-After`/`x-ratelimit-reset-after` values are clamped instead of reaching `Duration::from_secs_f64`.
- **Permission bits 41–52 match Discord's table.** The `PermissionFlags` name table was shifted by one from bit 41 upward, `permissions::SEND_POLLS` was bit 50 (really `USE_EXTERNAL_APPS`; `SEND_POLLS` is 49), and `PIN_MESSAGES` (51) and `BYPASS_SLOWMODE` (52) were missing. The table and constants now follow developers/topics/permissions.mdx, constants exist for every bit from 41 to 52, and the retired bit 47 (`USE_CLYDE_AI`) is no longer named.
- **Terminal gateway close codes stop the shard.** 4004 and 4010–4014 make `GatewayClient::run` return `DiscordError::Gateway` instead of reconnecting forever, including closes received before HELLO; 4007 and 4009 start a fresh session instead of a doomed RESUME. Per-connection heartbeat and outbound tasks are aborted on every exit path of a connection attempt, including cancellation during the shutdown flush. (Prompt shutdown of a whole multi-shard client is phase 2 work.)

- **Interaction responses track an in-flight phase.** Follow-ups, `edit_reply`, and `delete_reply` wait until Discord accepts the initial response instead of racing ahead of it, and a second initial response fails at once. A failed initial response rolls back only when Discord provably did not apply it (4xx, 429, local validation, connect failure); timeouts, 5xx, failed response reads, and cancelled futures leave `Uncertain`, which remembers every kind that may have landed. Retrying from there is safe: Discord's 40060 settles the state (to "acknowledged, kind unknown" when attempts of different kinds were uncertain), and a successful `@original` operation settles it too, even while a retry is in flight. A dropped future no longer leaves the slot claimed forever.
- **One owner per initial response across transports.** The typed HTTP interactions endpoint and REST responses share the initial-response slot; when the response goes over REST, the endpoint answers 202 with no body as Discord specifies instead of sending a second response. Inline responses are recorded, so retained clones (spawned tasks, `AppContext`) can follow up. `AppFramework` is `Clone`, as the docs already assumed.
- **Interaction tokens stay out of `Debug` output** for `InteractionContextData`, the interaction variants, `AppContext`, and the raw `InteractionContext` (including its raw payload).

- **Handlers can await `fetch_members` and collectors without stalling their shard.** Each shard applies events (cache, backend writes, voice, member-chunk correlation, collectors) in gateway order on an internal processor that never waits for handlers; handlers run in a bounded, tracked `JoinSet` (Serial = one at a time, Concurrent = `max_concurrent_handlers`, default 256) and their panics are contained. Serial mode used to deadlock until `fetch_members` timed out.
- **Event-stream gaps fail the shard instead of corrupting state.** Per-shard queues are bounded (`event_queue_capacity`, default 10,000) and the gateway reader never blocks; if an event cannot be admitted, or the processor or a dispatcher dies, the shard stops, its cache is invalidated, pending `fetch_members` calls fail, and `start()`/the supervisor return `DiscordError::Gateway`. `fetch_members` also requires every chunk index before returning.
- **Collectors created inside handlers no longer miss events.** The collector hub keeps a bounded, sequence-numbered journal; each handler delivery carries the cursor captured before it was queued, and `Context::*_collector()` replays from it before following live events (eviction surfaces as lag). `ctx.collectors().*` still starts from now.
- **Interactions get their own lane and deadline.** INTERACTION_CREATE has a separate queue, reserved slots (`max_concurrent_interactions`), receive timestamps (`Context::event_received_at`), and an admission deadline (`interaction_admission_timeout`, 2 s); interactions that cannot be admitted in time go to `on_interaction_overload`, which runs on its own bounded thread. The runtime never acknowledges an interaction itself.
- **READY no longer wipes other shards' cache.** `CacheHandle::clear_shard` drops only guilds owned by the shard (`(guild_id >> 22) % shard_count`), plus DMs on shard 0; users are kept.
- **External cache backend mirror is ordered, fenced, and self-healing.** One worker per client applies writes in order; a dropped or failed write quarantines that shard and runs an ordered resync with backoff. The store keeps one epoch: clears are compare-and-set with an idempotent `CacheClearId`, every write carries its epoch and is ignored when stale, so a delayed write or clear from an old client cannot resurrect or erase data. `Context::cache_backend_health()` reports health; shutdown reports unrecovered shards. The mirror supports one writing client per store, which deployments must enforce. MESSAGE_UPDATE is merged into the stored message (or skipped when no full copy exists), and the in-memory merge covers every message field.
- **Prompt, complete shard shutdown.** The supervisor watches all shards concurrently, stops the others on the first fatal error (also halting pending boot waves), returns that error from `start()`/`wait()`, aborts and joins tasks past `handler_shutdown_timeout`, and protects against cancellation from the moment the future is created. `ShardingManager::broadcast` reaches every shard even if one channel is closed, and guild-scoped gateway commands go to the shard that owns the guild.

- **Audio playback no longer blocks on stalled inputs or connections.** `AudioPlayer` reads each resource and drives each connection on separate tasks and handles commands immediately. Stop, pause, and replacement flush every connection before `TrackEnd`/`Paused` is published, so a sink honouring the `VoiceFrameSink` contract transmits no old-track audio afterwards. Every connection gets five silence frames and then speaking off when its audio stops, even after lagging; re-subscribing a sink hands the connection over serially.
- **Real-time voice delivery.** A frame must start sending within 60 ms and a send stalled for 60 ms is cancelled (audio is at most 120 ms late); a full queue drops the oldest frame; a recovering connection catches up at about twice real time. Untransmitted media becomes an RTP timestamp gap: `VoiceRuntimeHandle` advances sequence and timestamp only after a datagram is sent and never reuses a nonce (DAVE included). Underruns rebuffer, `unpause()` follows the same 60 ms rule, `AudioResource::next_pcm_frame` is cancel-safe, and panicking sinks/inputs are contained.
- **Voice interoperates with real Discord voice servers, for send and receive.** Both transport modes (`aead_aes256_gcm_rtpsize`, `aead_xchacha20_poly1305_rtpsize`) put the 32-bit packet counter in the last four bytes of the AEAD nonce instead of the first four, so Discord could not authenticate any packet the crate sent, and no received packet decrypted. Received packets with an RTP header extension also authenticated the extension body as additional data, although Discord encrypts it with the payload. The nonce now starts with the counter, as in @discordjs/voice and Songbird. Only the fixed header, the CSRCs, and the extension preamble are additional data, and the decrypted extension body is stripped before Opus/DAVE processing. RTP padding (P bit), which is also encrypted, is removed after decryption as RFC 3550 §5.1 describes, instead of reaching the Opus decoder or hiding a DAVE frame's magic marker; a padding count of zero or one longer than the payload is an error. The old tests encrypted with the same wrong layout, so they passed anyway. Known-answer vectors generated outside the crate (`ci/voice_transport_kat.py`, cross-checked against Node and libsodium) now pin both directions. DAVE frame encryption (`davey`) is unchanged.
- **DAVE receive passes silence packets through.** For a muted user, Discord's SFU sends the Opus silence frame `F8 FF FE` without DAVE encryption. `recv_voice_packet_with_dave`/`recv_decoded_voice_packet_with_dave` parsed it as a DAVE frame and failed with "DAVE frame is too short", which ended receive loops that used `?`. A payload that is exactly that frame is now returned unchanged without calling the decryptor, as the DAVE protocol specifies ([silence packets](https://daveprotocol.com/#silence-packets)); any other payload is still parsed as a DAVE frame.
- **Shard supervisor memory is bounded.** Every published `ShardSupervisorEvent` went into an unbounded channel that only `drain_events()` / `poll_event()` emptied, so a long-running client that only read `statuses()` kept every state change and error from reconnect churn. Draining also applied events a second time, so polling an older event rolled the status back (for example to `Running` while the shard was `Reconnecting`). Now `publish` alone updates the status. Events wait in a queue of at most 256 per shard; on overflow the oldest are dropped, and the next drain starts with `ShardSupervisorEvent::Lagged { shard_id, missed }`.
- **`drain_events()` survives a finished shard.** Once one shard's runtime ended (its publishers dropped, for example after a clean stop), every `drain_events()` call returned "event channel disconnected" and discarded the events it had already taken from that shard and the others, including `Lagged` markers. An ended shard is now drained like any other and then skipped, keeping its last status in `statuses()`. The call fails only when it has nothing to return and every registered shard has ended. `poll_event` still reports the disconnect per shard.

- **Multi-process sharding is bounded and IDENTIFY-coordinated.** Each child has its own bounded IPC writer with control-message priority on both sides, so a child that stops reading or writing no longer hides shutdown or grants; one deadline covers the whole shutdown (op → close stdin → keep reading → kill → confirmed reap); `wait()`/`shutdown()` agree and return every terminal failure (respawn exhaustion, spawn failure, unconfirmed kill, monitor panic). The parent grants every IDENTIFY — first connect, INVALID_SESSION, 4007/4009, reconnects before READY — per `shard_id % max_concurrency` bucket, keeps a bucket until the holder releases or its exit is confirmed, and enforces the daily session-start budget across refreshes. IPC frames carry an `@discordrs-ipc/1 ` prefix and a size cap, so stray stdout no longer corrupts the protocol; child request handlers are capped and cancellable. Commands queued while disconnected are kept in one bounded backlog (newest presence wins, at most 32 others, drops logged by kind only).
- **In-process shards share one IDENTIFY gate and the session-start budget.** `spawn_shards`/`spawn_auto_shards` (and `start_shards`/`start_auto_shards`) staggered only the first boot and spaced IDENTIFYs per shard, so two shards of one `shard_id % max_concurrency` bucket that lost their sessions together (for example both closed with 4009) identified at the same moment, and Discord rejects an IDENTIFY that breaks the bucket's 5-second window. The session-start budget was looked at once: `remaining == 0` delayed the boot, but with `remaining = 1` and two shards both identified, manual `spawn_shards` ignored the budget, and re-IDENTIFYs after INVALID_SESSION, 4007/4009, or a reconnect before READY were never counted, although exceeding the budget makes Discord reset the bot token. All shards of a client now share the bucket queues and budget accounting of `ProcessShardManager`: one IDENTIFY per bucket every 5 seconds, each one counted, and one the budget cannot cover waits for the reset, where `/gateway/bot` is read again (`Shutdown` still ends the wait at once). A budget below the shard count at startup starts the shards that fit and logs how many wait. `spawn_shards` now returns the `/gateway/bot` error instead of starting without the budget, unless `ClientBuilder::identify_gate` supplies a gate of your own, which then owns both limits.

- Voice CLIENTS_CONNECT entries whose SSRC exceeds 32 bits are ignored instead of being truncated onto another SSRC; `EmbedBuilder` timestamps no longer wrap the year beyond 2³¹; the first heartbeat delay keeps sub-millisecond precision; a corrupt zlib byte counter is an error instead of a wrapped slice index.
- 15 broken intra-doc links are fixed, and CI fails on rustdoc warnings (all and default features).

- `Webhook::kind` reads and writes Discord's `type` key (2.x used `kind` on the wire and never decoded the value).
- Guild, channel, and gateway models are smaller (`Channel` 536 → 488 bytes, `Guild` 856 → 784), and decoding a GUILD_CREATE allocates 200 fewer times (presence status is interned).

- **Modal checkbox and radio submissions parse.** Discord sends a submitted checkbox as `value: true|false`; the parser read a `checked` key and the model stored `value` as a string, so every modal containing a checkbox failed to parse. A radio group with nothing selected (`value: null`) was rejected too. `CheckboxBuilder` sent its initial state as `checked` instead of Discord's `default`. All ten documented modal-submit payloads now parse with their values.

- **Gateway memory and CPU (phase 4).** Dispatches are no longer parsed into a `serde_json::Value` tree and cloned three times: the read loop scans only `op`/`s`/`t` and a borrowed `d`, copies `d` once into the bounded queue, and the processor decodes typed payloads straight from that text. Events carry the raw payload only when asked. Handlers and collectors share one `Arc<Event>` (128 bytes instead of a 4,848-byte inline enum), the collector journal stores those `Arc`s, and the cache shares the event's `Arc<Message>` / `Arc<Member>` / `Arc<Presence>` instead of cloning them. Measured with `tests/perf_report` (deterministic allocation counts): a 1,000-member GUILD_CREATE 508,698 → 20,921 allocations and 34.7 → 3.2 MB peak heap; MESSAGE_CREATE 573 → 23 allocations (20 after checkpoint C); INTERACTION_CREATE 1,519 → 66 (67 after checkpoint C, which also decodes more fields); live heap after 25 large guilds 386 → 87 MB; an empty collector hub 1.24 MB → 2.2 KB; extra collectors no longer copy events they don't match. Numbers and method: `docs/design/perf-baseline.md`.
- An unavailable GUILD_CREATE (`{"id": …, "unavailable": true}`) decodes as its own payload variant instead of failing.
- MESSAGE_UPDATE's partial author is applied as a patch to the cached user (an omitted field keeps its value, `null` clears it) instead of replacing the user.
- READY's `session_id` and `resume_gateway_url` are read independently, so a malformed one no longer discards the other.
- Message component interactions keep `data.resolved` and `data.id`; interactions keep `guild`, `channel`, `message`, `attachment_size_limit`, and `version`; resolved channels keep `permissions` / `app_permissions`; attachments keep `proxy_url`, `placeholder`, and `placeholder_version`. `Interaction::Unknown.raw_data` keeps `data` byte for byte in any key order.

- **Message flag values.** `MessageFlags::SUPPRESS_NOTIFICATIONS` was `1 << 10` and `IS_VOICE_MESSAGE` was `1 << 12`; Discord's values are `1 << 12` (4096) and `1 << 13` (8192). A message sent with "suppress notifications" therefore went out with a reserved bit, and a voice-message flag was read as "suppress notifications". `HAS_SNAPSHOT` (`1 << 14`) is added, and a test pins every flag to its documented value.

- **Presence activities decode the shape Discord sends.** A read-only run against live Discord with the presence intent failed 11 of 30 GUILD_CREATE dispatches (`invalid type: string "…", expected struct ActivityButton`), so those guilds never reached the cache: over the gateway an activity's `buttons` is an array of label strings (bots cannot see the URLs), and the model expected the `{label, url}` objects that are only sent. `Activity::buttons` is now `Option<Vec<String>>` and reads both shapes. PRESENCE_UPDATE dropped *every* activity of a presence when one did not decode; it now decodes activities one at a time and drops only that one. GUILD_CREATE and GUILD_MEMBERS_CHUNK keep their strict fast path and, only when it fails, decode members, presences (and each activity), and voice states element by element, leaving out the ones that do not decode with a `warn!` that counts them (its reason is the error category, the expected type or missing field, and the position; no value from the payload) instead of losing the guild or the chunk; the guild's own fields, channels, threads, and roles stay strict. A dropped element does not delete what the cache already holds for that user, which keeps its earlier value until a later event replaces it. `Context::fetch_members` does not report such a chunk as a complete fetch: it returns `DiscordError::IncompleteMemberFetch` with the members that decoded and the number dropped (`GuildMembersChunkPayload::dropped_members` counts them per chunk). Activity `secrets.match` is read from Discord's `match` key (2.x used `match_secret` on the wire). Added the documented fields that were missing: `Activity::{status_display_type (StatusDisplayType), details_url, state_url, instance, flags}`, `ActivityAssets::{large_url, small_url, invite_cover_image}`, and `ClientStatus::vr`. `Activity::assets` and `secrets` are boxed (most cached activities have neither), so with the new fields an activity shrinks from 440 to 352 bytes, and activity lists start at two slots instead of four: a 1,000-member GUILD_CREATE takes 500 fewer allocations and 29% fewer bytes, PRESENCE_UPDATE 40% fewer bytes, and the 25-guild storm retains 4% less.

- **Interaction callbacks are not held by the bot's global rate limit.** Every REST request waited out the shared global deadline, so when any call got a global 429, `defer()` and the other initial callbacks waited the whole retry-after and missed Discord's three-second deadline. The interaction-token routes (initial callback, `@original` get/edit/delete, follow-up create/get/edit/delete), which Discord does not bind to the global limit, no longer wait for the bot's global deadline. Requests sent without an `Authorization` header (interaction and webhook token routes, public routes), which Discord limits per IP address, share a separate global deadline: a global 429 on any of them holds all of them, including interaction routes with other tokens, but no bot-token request, and a bot-token global 429 no longer holds interaction routes. The route manifest marks the interaction routes with a new `interaction` auth kind; webhook-token routes and raw requests still honour the bot's global block as well.
- **Autocomplete no longer shares the command's route and cooldown in `AppFramework`.** Autocomplete was routed as `RouteKey::Command(name)`, so typing an option started the command's cooldown, later autocompletes were answered with the cooldown message (Discord accepts only choices for autocomplete), and the command itself was then refused. Autocomplete now has its own `RouteKey::Autocomplete(name)` and `AppFrameworkBuilder::autocomplete(name, handler)`, with no cooldown unless one is set for that key. An autocomplete interaction is answered with no choices when a guard or cooldown rejects it, no autocomplete route matches (the command's handler no longer runs on every keystroke), or its route returns another response type.
- **Large interactions are no longer rejected with 413.** The interactions endpoint read at most 64 KiB, and a channel select with 25 resolved forum channels carrying 4,096-character topics (104,741 bytes) was answered `413 Payload Too Large` before the handler ran. The default is now 1 MiB (`DEFAULT_INTERACTION_BODY_LIMIT`; the size estimate is documented there), and `InteractionsEndpointBuilder::body_limit(bytes)` sets another limit.
- **GUILD_CREATE respects the metadata cache caps.** `apply_guild_create` inserted every emoji, sticker, stage instance, and soundboard sound without evicting, so `max_emojis`, `max_stickers`, `max_stage_instances`, and `max_soundboard_sounds` were exceeded until a later single-entity event. GUILD_CREATE now evicts like the other paths; the caps count all guilds together, oldest entries first.

The raw payload is `event.raw()`, kept only with `ClientBuilder::keep_raw_events(true)` and always for unknown or undecodable dispatches; payload wrapper structs and their `raw` fields are removed. `decode_event` takes `&str`.
- **Handlers** (breaking). `EventHandler::handle_event` takes `Arc<Event>`. Typed hooks receive the payload as the event stores it, without a copy: `Arc<Message>`, `Arc<MessageUpdate>`, `Arc<Member>`, `&GuildCreate`, or a reference; `raw_event(ctx, &str, &RawValue)`; decode failures go to the new `decode_failed` hook instead of `raw_event`.
- **Collectors** (breaking). `EventSubscription::recv` returns `Arc<Event>`; `MessageCollector` collects MESSAGE_CREATE only (updates go to `MessageUpdateCollector`); `next()` copies only matching payloads.
- **Cache and backends** (breaking). `apply_guild_create(&GuildCreate)`; `upsert_message` / `upsert_member` / `upsert_presence` / `upsert_guild` accept `impl Into<Arc<T>>`; `CacheBackend::put_member` / `put_message` / `put_presence` take `Arc<T>`, and MESSAGE_UPDATE reaches backends as a typed patch merged in the ordered worker (never a fabricated full message).
- **One JSON reader** (breaking for error text). REST responses, webhook events, voice gateway frames, and interactions decode from text with the same reader as the gateway, so each model is compiled once. REST decode errors now include positions, and duplicate struct keys are an error.
- **Typed model values** (breaking). Command option values and choices are `CommandOptionValue` (`String` / `Integer` / `Number` / `Boolean`; `ApplicationCommandOptionChoice::new` and `CommandOptionBuilder::choice` take `Into<CommandOptionValue>`, other values go through `try_new` / `try_choice`, which with command `validate()` enforce Discord's types and ±2^53 ranges). The remaining `Value` fields are typed (embed provider, audit-log options, application team / install params / integration types config, onboarding prompts, guild scheduled events, invite partials, connection integrations) or kept as `Box<RawValue>` where Discord leaves the shape open (audit-log change values with `new_value_as` / `old_value_as`, unknown interaction data, identity metadata, SKU fields, template source guild). Interaction `type` must be a number and `data` an object; repeated documented keys are rejected.

- **Builders build typed request models** (breaking). No builder holds or returns `serde_json::Value`: `MessageBuilder::build()` returns `request::CreateMessage`, `ContainerBuilder::build()` a `Container`, `ComponentsV2Message::build()` a `Vec<Component>`, `EmbedBuilder::build()` a `request::Embed`. `ActionRowBuilder` builds a button row; a select builder is itself a row (`add_select_menu`, `add_text_input`, and `add_component(Value)` are removed). `SelectMenuBuilder::{string, user, role, mentionable, channel}` return per-kind builders, so a value the select kind cannot hold does not compile; the generic `default_value(SelectDefaultValue)` / `default_values(Vec<…>)` are replaced by typed setters. `SectionBuilder` tracks its required accessory in its type. Encoding a Components V2 message takes 26 allocations instead of 313, and an interaction reply 27 instead of 406.
- **Interaction responses** (breaking). Handlers, routes, and guards return `EndpointReply`; the 2.x `interactions::InteractionResponse` enum and the `Value`-based callback data are replaced by `request::InteractionResponse`. `ModalBuilder` wraps inputs in Labels by default; the action-row text-input wrapper Discord deprecated is reachable only through deprecated constructors. The callback body (including attachment content types) is built and checked before the response slot is claimed, so a local error leaves the interaction unacknowledged and an inline fallback still answers.

- **REST surface** (breaking). Every endpoint takes its concrete request type (`ModifyChannel`, `ModifyGuildMember`, `CreateGuildRole`, `request::CreateMessage`, `request::ExecuteWebhook`, …) and returns a typed model; no public domain method takes `serde_json::Value` or an unconstrained `B: Serialize` (documented exceptions: Slack/GitHub-compatible webhook bodies and application-defined metadata). The 41 `_typed` pairs and 5 standalone `_typed` methods are folded into the canonical names; 35 one-to-one renames (`_from_request`, `_config`, non-generic `_typed`) remain as deprecated forwards and 35 untyped variants are removed; the migration table is on the docs site (REST → "Migrating from 2.x"). Request bodies are encoded once into bytes and reused across retries. The Components V2 helpers (`send_container_message`, `send_to_channel`, `send_components_v2`, `edit_message_with_container`) build typed requests, return `Message`, and get the client's default `allowed_mentions`. Forum tag lists take `request::AvailableForumTag`, so a new tag needs only a name.

- **Shared cache objects and typed partial updates** (phase 4 checkpoint C, breaking). `Member::user` and `Message::author` are `Option<Arc<User>>` (same JSON) shared with the user store (`upsert_user(impl Into<Arc<User>>)`, `user_arc`); channel and role stores hold `Arc`s (`EventKind::ChannelCreate/ChannelUpdate(Arc<Channel>)`, `ThreadEvent::thread: Arc<Channel>`, `RoleEvent::role: Arc<Role>`, `GuildCreate::roles`, `channel_arc`), and `guild()` / `guilds()` fill roles from the role store; storing a full guild replaces its roles. GUILD_MEMBERS_CHUNK carries `Vec<Arc<Member>>` and `Context::fetch_members` returns `Vec<Arc<Member>>`. PRESENCE_UPDATE is `PresenceUpdateEvent { guild_id, user: Option<PartialUser>, presence: Arc<Presence> }` (`PresenceUpdateUser` removed). GUILD_MEMBER_UPDATE decodes to `MemberUpdate` (hook takes `Arc<MemberUpdate>`, `CacheHandle::apply_member_update`) and GUILD_UPDATE to `GuildUpdate` (hook takes `&GuildUpdate`, `apply_guild_update` returns `Option<Arc<Guild>>`, GUILD_CREATE-only fields survive). Partial updates patch cached objects copy-on-write and never create cache entries: an uncached member or guild is not stored from an update. Measured: guild cache apply 31,291 → 670 allocations, 25-guild storm heap 87 → 64 MB, GUILD_CREATE 20,921 → 17,744 allocations.

- **REST bodies live in `discordrs::request`** (breaking). The 49 request bodies that were still in `model` (`ModifyGuild`, `CreateGuildRole`, `ModifyGuildMember`, `CreateGuildChannel`, …) moved to `request` unchanged apart from being Serialize-only (public fields and `Default` where they had it). `discordrs::X` (and the prelude, for the types it re-exports) keep working; `model::X` is a deprecated alias until 4.0. The crate-root `CreateMessage` / `CreatePoll` now name the `request` types. Removed: the 2.x `model::CreateMessage` (JSON `components` / `embeds`), the 2.x `model::CreatePoll`, `InteractionCallbackResponse` and `create_interaction_response_typed` (use `create_interaction_response(&InteractionResponse)`, with `InteractionResponse::Raw` for callbacks the enum doesn't model), and `discordrs::Error` / `types::Error` / `error::BoxError` (deprecated since 0.4).

### Deprecated
- `RestClient::create_guild`, `delete_guild`, `create_guild_from_template`, and `modify_guild_mfa_level`, plus `Guild::delete` and `Guild::set_mfa_level`: Discord removed guild creation by applications on 2025-07-15 and transferred bot-owned guilds to users, and dropped these routes from its docs. They will be removed in the next major release.
- 11 interaction helpers duplicated by `InteractionResponder` (`defer_interaction`, `defer_update_interaction`, `update_interaction_message`, `respond_with_modal_typed`, `respond_with_autocomplete_choices`, `followup_message`, `get_original_response`, `edit_original_response`, `delete_original_response`, `edit_followup_response`, `delete_followup_response`); id/token-only helpers are documented as stateless.
- `interactions_endpoint` and `typed_interactions_endpoint`, which panic on an invalid public key: use `try_interactions_endpoint` / `try_typed_interactions_endpoint`.
- `ButtonBuilder`: use `CustomButtonBuilder`, `LinkButtonBuilder`, or `PremiumButtonBuilder` (`Button::try_from(ButtonBuilder)` converts; a premium style or missing `custom_id` fails). `InteractionResponse::PremiumRequired` (Discord deprecated it; use a premium button).
- The 35 one-to-one REST renames listed in the migration table (deprecated forwards that send the same request as the canonical method).

### Changed
- GUILD_CREATE now populates the channel, thread, member, user, voice-state, presence, emoji, sticker, and stage-instance caches under a single write lock; the cached `Guild` is stored with bulk collections stripped to avoid double storage. GUILD_MEMBERS_CHUNK and THREAD_* events are cached too.
- The REST transport is unified into one retry loop: the per-route serialization gate now covers **all** requests (previously JSON requests bypassed it, allowing same-bucket 429 races), 5xx responses and transient transport errors retry with backoff (0.5s/1s/2s), 429 handling reads the `Retry-After` header and `x-ratelimit-scope`/`x-ratelimit-global` headers (Cloudflare-level bans with HTML bodies now back off correctly), and the route-gate map is garbage-collected.
- The gateway now paces IDENTIFY to Discord's 1-per-5s-per-shard limit, and short-lived sessions (< 30s) reconnect with escalating backoff instead of immediately, preventing tight reconnect/re-IDENTIFY loops on repeated INVALID_SESSION.

- Cache hot paths rewritten: LRU order tracking moved from `VecDeque` scans (O(n) per insert) to an ordered-map structure (O(log n)), per-guild member and per-channel message caps use incremental counters instead of full-map scans, TTL sweeps are throttled to once per 5s, and list reads filter expired entries per-entry under a read lock instead of upgrading to a write lock.
- The voice manager write lock is now taken only for voice events instead of on every dispatch.
- Gateway protocol failures (missing Hello, decode errors, terminal close codes, command-queue overflow) now surface as `DiscordError::Gateway` instead of `DiscordError::Model`.
- `RestClient` is now `Clone` (clones share rate-limit state, the connection pool, and the application id).
- Component-interaction channel stubs no longer overwrite fully-cached channels (insert-if-absent).
